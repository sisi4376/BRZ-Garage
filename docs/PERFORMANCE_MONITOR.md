# 仪表被动性能监测

固件 4.0.4 起 `CONFIG_OBD_PERF_MONITOR` 默认关闭，正式修复镜像也关闭此项。
需要诊断时手动设置 `CONFIG_OBD_PERF_MONITOR=y`。通过现有串口读取 `gauge_perf` 日志，
每约 10 秒输出一个窗口；无需手机连接或发送诊断指令。监测不改变 PID 顺序、
轮询间隔、ELM 参数、缓存数值、显示滤波参数、任务优先级或 BLE 数据协议。

## 对采集链路的约束

- 热路径只读微秒时间戳并尝试写入固定 256 条的 RAM 环形缓冲区。
- 多生产者只尝试一次原子取得访问权；竞争或满队列时立即丢弃**监测事件**。
  不等待、不重试取得锁、不分配内存、不打印、不写 NVS、不额外查询 OBD。
- 低优先级任务（1，低于现有 OBD/LVGL 的 4）每 100ms 最多取 256 条事件，
  每约 10 秒汇总串口输出。任务创建失败仅关闭监测，不中止仪表启动。
  在核心任务、显示、BLE 初始化及 15 秒启动健康检查通过之后才尝试分配。
- 缓冲区约 4KB，另有统计结构与 4KB 后台任务栈。队列和统计结构不再常驻静态 RAM，
  仅在启动监测时申请内部内存；任务创建失败会释放申请的结构。生产者发布前保持关闭。
  分配前要求可用内部堆足够覆盖分配预算后再保留 32KB，最大连续块也必须覆盖预算。
  这是一项保守准入检查，不是对未来无线/OTA 分配的硬性内存预留。所有耗时运算和格式化在后台完成。
- 时间戳和原子操作仍有少量执行开销，不能承诺物理上的零开销。
  关闭配置可编译移除采集钩子，做同条件实车 A/B 对照。没有实车数据前，不将主机测试
  或目标编译成功当作“采样频率绝对不变”的证明。

## 日志读法

所有 `us` 都是微秒，`hz_x10=125` 表示 12.5Hz。`avg/max` 是本窗口平均值与最大值。

| 字段 | 含义 |
|---|---|
| `window_ms` | 实际统计窗口长度；后台被抢占时可能长于 10 秒 |
| `loss_marks` | 启动以来监测丢事件的标记数，并发丢弃可能合并计数；不是车辆数据丢包数 |
| `ui_pages` | 本窗口显示页面位图：`01` 其他、`02` 挡位+转速、`04` 独立转速、`08` 车速、`10` 指针；切页时按位合并 |
| `flash_ticks` | 本窗口处于转速闪烁状态的 UI 回调次数 |
| `rpm/speed count, hz_x10` | 默认 ELM 解码回调收到的有效样本次数与频率，包括数值没变化的样本 |
| `gap_us` | 相邻有效样本间隔；看最大值可发现间歇性停顿 |
| `cmd=010C/010D` | 转速/车速请求；其他 PID 各自单独统计；`FFFF` 为 AT/未单列命令 |
| `sent` | 提交 BLE 写入前的请求尝试次数，可能包括写入失败；不是 ECU 成功处理次数 |
| `done` | 收到结束符的请求数，包含 `NO DATA` 和之后被解析器丢弃的响应，不能当成有效样本数 |
| `first_us` | 成功完成的请求从提交到首次 BLE 通知的时间；首包不一定含有效数据 |
| `prompt_us` | 提交到包含结束符的 BLE 通知到达处理函数的时间；在原有唤醒逻辑之前观测，不移动唤醒时机 |
| `rpm_cache/speed_cache` | 默认回调中的缓存更新/挡位推算耗时；speed 还包括现有车速修正 |
| `parse` | 完整普通 OBD 响应的解析区间，包含内部缓存更新；不包括等待分包的时间 |
| `ui_callback` | 一次仪表 UI 定时器回调的耗时；`ui gap_us` 是实际回调起始间隔 |
| `lv_handler` | LVGL 定时器处理整体耗时，包含 UI 回调与绘制等工作，不能与它们简单相加 |
| `lv_refresh` | LVGL 自带 monitor 回调报告的一轮刷新耗时/像素量；像素按 16 取整 |
| `cancel(...)` | 写入失败、等待超时、ELM 断连、响应被丢弃的次数 |

`lv_refresh` 不是屏幕光学刷新率，也不是逐条 SPI DMA 完成时间；不在 DMA 中断中追加
监测逻辑。无重绘时没有该事件。不同页面、开机动画和闪烁会改变 UI 负载，应分别采集窗口。
RPM/speed 测量针对默认 ELM 回调，不含展厅模拟、ESP-NOW 从表注入或自定义回调。
CAN 被动监听不是普通一问一答，不能用其 ATMA 命令耗时判断 PID 吞吐。

断连/取消后打断样本连续性；时间戳按无符号差值处理短区间回绕。
监测丢事件或请求取消后打断请求配对和样本间隔，重新见到一个结束符后才恢复请求配对，
保守跳过可能属于旧请求的响应，避免错误计算跨请求耗时。
若某窗口 `loss_marks` 增长，该窗口频率可能低估，只适合提示负载，不用于精确比较。
请求跨窗口时保留关联，所以单窗口 `done` 可以大于 `sent`。

## 定位方法

1. 采集普通转速页/车速页至少 3 个稳定窗口，再单独采集高转速闪烁窗口。
2. `prompt_us` 大、解析和缓存耗时小：优先查适配器/ECU/BLE。
3. 单请求很快，但 speed 间隔明显大：查轮询分配与其他 PID 占用。
4. 原始采样稳定，`ui gap_us`、`lv_handler` 或 `lv_refresh` 最大值大：查界面负载。
5. 各阶段都快但显示追随慢：结合既有 55/90ms 平滑时间常数判断。

本模块只观测，不自动调频、不改适配器参数、不调整显示平滑。

## 4.0.3 内存回归与 4.0.4 启动检查

故障设备实机确认 `trip_stat: failed to create mileage task`，随后监测也因内存不足关闭。
旧监测即使无法创建任务，约 5KB 静态内部内存仍被占用。统计任务未启动使油耗一直显示
`--`，并停止新增行程统计。单独的转速/车速采集仍可运行。

4.0.4 在显示 DMA 和无线初始化前创建统计任务，检查创建结果；失败直接报告核心启动错误。
统计任务完成每轮统计/检查点后发布计数与心跳。主任务复用自己的栈等待 15 秒，确认计数增长且
心跳不超过 2 秒才确认 OTA；不依赖 ECU 是否连接。从表明确跳过本机统计要求。不再另建 4KB
的 OTA 确认任务。保持 4.0.2/4.0.3 存储与协议布局不变，避免旧固件降级造成数据丢失。

`tests/test_firmware_startup.py` 运行生产代码，覆盖创建失败/重试、无 ECU 的真实统计循环、
停滞/过期心跳拒绝确认 OTA、计数/时钟回绕，以及监测准入、分配失败释放和重复启动。
主机测试与构建不能代替安装后的冷启动和实车油耗验证。
