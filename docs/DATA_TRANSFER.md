# 手动数据迁移（Android 4.3.1 / 鸿蒙 0.3.2）

适用于偶尔切换手机：旧手机与仪表同步 → 导出 ZIP → 新手机合并导入 → 绑定同一仪表继续同步。无需账号、云服务或仪表固件升级。安卓与鸿蒙原生版统一使用 v3 ZIP/JSON 数据包，并继续支持 v1/v2 导入。主目录旧 Android 4.2.2 不能读取 v3，必须先升级。鸿蒙工程位于 `codex/harmony-app` 工作树，具体修复与验证范围见 [平台对齐记录](APP_PLATFORM_PARITY.md)。

## 使用方法

1. 在旧手机覆盖安装 Android 4.3.1 / 鸿蒙 0.3.2 或更新版本，先完成一次仪表同步。
2. 打开 **设置 → 应用 → 数据迁移 → 导出完整数据包**，通过系统文件选择器保存 ZIP。
3. 将文件传到新手机，安装同版或支持该数据包格式的新版本。
4. 进入 **导入并合并数据包**。检查导出时间、来源仪表、记录数量和冲突数。
5. 切换设备通常选择“以数据包为准”；如果要保留新手机的冲突记录，选择“保留本机冲突内容”。确认后先自动生成本机备份，再执行合并。
6. 返回设置，在新手机上完成蓝牙绑定和权限授权，连接来源仪表。导入不会复制系统配对、用户同意记录或授权。

经典设置页也提供独立的“数据迁移”入口。导出与导入期间暂时停止手机 BLE 同步服务，操作结束后按原自动连接偏好恢复。正在 OTA 时拒绝开始迁移。

导出后继续在旧手机编辑的数据不在旧数据包中，需要重新导出。导出文件未加密，应妥善保存。系统文件选择器可以选择本地或已接入系统的文件提供方，App 本身不新增联网同步逻辑。

## 数据范围与合并规则

- 普通行程、时间/数据修订、手动拆分、OBD 轮询证据及行程删除标记。
- 手工加油记录，包括草稿、加满状态；保养和日常费用。
- 仪表加油区间、区间修订与历史版本；自定义区间的名称、历史和当前统计起点。
- 车辆名称、车型、车牌、油箱及续航参数、手动油量校准、里程校准与显示偏好。
- v3 增加按仪表保存的车辆快照缓存、最近油量、当前加油区间、仪表设置、固件信息与授时状态，及首页/设置布局和车辆外观偏好。缓存按各组更新时间合并，页面应继续显示缓存的采样时间。
- 不传输蓝牙配对、权限、自动连接开关、用户同意、OTA 状态和待执行仪表命令。

导入后用数据包的车辆标识读取离线数据，首页缓存、里程校准、保养及日常费用无需先绑定仪表即可显示；关闭并重新打开 App 后继续保留。已有本机蓝牙绑定优先，绑定其他仪表时不混入来源车辆的缓存或记录。来源未指定车辆、且包中只有一个有效仪表标识时自动恢复该标识；多个标识时不猜测。

绑定前录入的费用使用 `device_id="local"`，两端均可导出和导入，绑定后继续计入费用与保养跟踪。该标识仅允许费用表使用，不允许普通行程、仪表区间或设备缓存使用。目标配置为空时接收来源配置，不将空值视为“保留本机”的有效冲突。

行程使用 `(device_id, trip_id)`，仪表加油区间使用 `(device_id, interval_id)` 去重。手机独有记录新增稳定 `transfer_id`；原本各数据库中的自增数字仅作为本机 UI 行号，不用于跨设备匹配。升级时给已有记录一次性补充标识，新建记录通过 SQLite 触发器生成标识；删除产生独立标记。A → B → C 以及重复导入保留相同标识。

目标没有的记录新增；相同记录跳过；内容冲突按导入页选择处理。目标独有记录保留，不以“包里不存在”推断删除。源数据包中的明确删除标记会参与冲突处理。手动拆分的原行程、两个子行程及相关删除标记作为一个整体选择，防止同时计入父子行程。仪表加油历史版本不同的车辆，其区间历史和版本整体选择，不能拼接不同代次的相邻区间。

首次升级之前，两台手机独立录入、但看起来相同的记账没有共同标识，仍视为不同记录；不会根据金额/日期擅自合并。普通行程继承现有仪表地址身份，尚不处理仪表恢复出厂后 ID 重用或跨平台地址映射。

新安装不再自动插入开发者的预置加油记录；已有数据库的记录全部保留。自定义区间不再于新增时裁剪到 50 条，避免导入的历史随后被自动清除。

## 文件格式 v3（兼容导入 v1/v2）

v3 在 `data.json` 增加 `devices`，以仪表地址为键，保存明确类型的缓存字段。Android 4.3.1 和鸿蒙 0.3.2 使用这一格式。旧 v1/v2 包不含这些字段，导入后应连接仪表补齐首页；不存在的数据不会伪造。v3 的历史九类表沿用 v2 字段。

App 4.2.1 导出 v2 格式，保养费用增加独立的 `maintenance_type`：1=A保、2=B保、3=轮胎更换、4=其他维修；历史未指定类型可为空。项目仍保存在 `title`，备注、金额、里程等字段不变。v1 数据包导入时自动补空类型，保留原记录；App 4.2.0 不支持 v2 包，接收手机须先升级到 4.2.1 或更新版本。

ZIP 仅包含 `manifest.json` 与 `data.json`。不将 ZIP 内容解压到文件路径。

- `manifest.json`：`format="brz-garage-transfer"`、`version=3`（旧包为 1/2）、`appVersion`、Unix 毫秒 `createdAt`、来源 `gauge`、数据 UTF-8 字节数 `bytes`、`sha256`。
- `data.json`：`tables`、`preferences` 和 `devices`（v1/v2 无 `devices`）。
- 数据表：`trips`、`deleted_trips`、`fuel`、`expenses`、`refuel`、`custom`、`fuel_deleted`、`expenses_deleted`、`custom_deleted`。
- 配置显式携带类型；`value=null` 表示该项使用默认值/未配置，合并时可以清除目标旧值。
- 整数字段使用 JSON 整数，浮点使用有限非负 JSON 数值。字段与主键契约定义于 `TransferSchema.kt`。
- 导入限制：manifest 8 KiB，未压缩数据 32 MiB，最多 100000 条记录；未知版本、缺表、异常路径、重复键值标识、非法类型和校验不符均拒绝。

SHA-256 用于检测损坏，不代表文件来源经过身份认证。不要编辑包内文件后自行修改校验值。

## 一致性与故障恢复

导入事务前完整校验数据包，合并前在 App 私有目录 `files/transfer-backups` 写入并验证本机完整包。备份创建失败则不修改业务数据。入口“导入前备份”可将这些包另存到文件，或按相同规则再次合并。**合并旧备份不是整库回滚，不删除之后新建的记录。**

五个业务数据库通过磁盘主库和 SQLite ATTACH 在同一事务中修改，使用 DELETE 回滚日志及 FULL 同步级别。提交失败时全部回滚。配置变更先写入主库的 `transfer_preferences`，随业务数据提交后应用到 SharedPreferences；进程启动时由 `BrzApplication` 重放尚未完成的配置提交。配置恢复失败期间不启动自动 BLE 同步。

导入成功后记录持久化的行程/加油区间重核标记。下次连接从 0 游标重新读取仪表保留窗口，不直接依赖合并后的最大编号；完整结束对应下载后才清除标记。手机已修订数据与删除标记继续通过现有 upsert 规则保留。旧协议（元数据 v1/v2）仍使用原固件 ACK 行为，不具备保留窗口重核能力。

仪表仍只保留最近 64 条行程和 20 条加油区间。数据包和仪表都没有的历史无法恢复；本功能没有扩容仪表，也不声称能恢复此前丢失的数据。
